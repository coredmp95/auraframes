  Plan 11-05 established, from the raw JSON payload rather than the parsed model, that
  `/frames/{id}/assets.json` NEVER sends a `created_at` key for any asset — not null, structurally

<objective>
Make `reconcile.py`'s removal path reachable against an API that never sends `created_at`, then
use it to answer D-16 — the question this phase existed to answer and did not: does anything at
all clear a stuck placeholder row?

Purpose: 11-05 closed every other phase-11 requirement but left REL-05's removal half untested
while REQUIREMENTS.md marked REL-05 complete. The requirement reads "and removes them if a working
mechanism is found" — no mechanism was ever attempted, so the condition was never evaluated. This
plan either finds a working mechanism or produces a dated, evidenced negative. Both are real
answers; the current state is neither.

Output: an explicit opt-in on the age guard with the default untouched, a named CLI flag, a live
probe of at most three rows with each mechanism's raw output recorded, and an honest REL-05 status.
</objective>

  <read_first>
    - `auraframes/reconcile.py` — `classify_placeholders`, `_creation_instant`, `ReconcileResult`,
      `apply_reconciliation` and `RECONCILE_PROBE_CANDIDATE_LIMIT`. Read the D-13/D-14/D-15
      docstrings in full; they state the intent this task preserves.
    - `tests/test_reconcile.py` — the existing predicate and age-guard tests, which must all still

    - `.planning/phases/11-write-path-reliability-format-support/11-LIVE-FINDINGS.md` — the
      `created_at`-never-sent evidence and the deferred-decision reasoning.
  </read_first>

  <files>auraframes/reconcile.py, tests/test_reconcile.py</files>

  <what-to-build>
Add an explicit, caller-named opt-in to `classify_placeholders` that promotes unresolvable-creation-time
rows into the eligible (`stuck`) bucket instead of parking them in `unknown_age`. The exact shape is
yours to choose — a keyword-only enum/string policy argument reads better than a bare boolean and
leaves room for a future third case — but it MUST satisfy:

- The default value reproduces today's behaviour exactly. A call with no new argument is
  byte-for-byte equivalent to today: unknown instant → `unknown_age`, never `stuck`.
- The opt-in is impossible to trigger by accident: keyword-only, no truthy-coercion of a stray
  positional, and named for what it does.
- The three-way-null predicate is UNTOUCHED. Do not widen, narrow or refactor it.
- `recently_created` semantics are untouched: a row with a RESOLVABLE instant that is simply too
  young must still land in `recently_created` regardless of the opt-in. The opt-in governs only the
  unresolvable case.
- Update the D-15 docstring to state the new rule honestly, including why the unconditional form
  made the feature inert rather than conservative.

Then expose it on the CLI as its own explicitly named flag, so `reconcile --remove` alone keeps
today's semantics and cannot touch unknown-age rows. Document the flag in `docs/CLI.md` including
the reason it exists.
  </what-to-build>

  <acceptance_criteria>
    - Every pre-existing test in `tests/test_reconcile.py` passes UNMODIFIED. If a pre-existing test
      needs editing to pass, the default was changed — revert and rethink.
    - A new test proves the default still parks an unknown-instant row in `unknown_age`.
    - A new test proves the opt-in promotes that same row to `stuck`.
    - A new test proves the opt-in does NOT promote a resolvable-but-too-young row out of
      `recently_created`.
    - A new test proves a video-shaped asset (hashless but carrying `file_name` and `uploaded_at`)
      is still excluded entirely under the opt-in.
    - `uv run pytest -m "not live" -q` is green.
  </acceptance_criteria>

  <done>The removal path is reachable under an explicit opt-in, and the default is provably unchanged.</done>
