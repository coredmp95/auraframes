<objective>
Make a transient HTTP 401 on a write chunk a recoverable, honestly-named event instead of a
run-ending mystery: re-login once per run, probe each item in the failed chunk with the
already-existing read endpoint, re-send only the items that genuinely are not there, and
charge the whole thing to the write budget on purpose.

Purpose: v2.0 lost roughly 4 in 10 live `sync --apply` runs to a 401 that was neither an auth
problem nor a geofence, and the debug session that chased it burned a day. A failure that
cannot say what it is, is the defect. This plan gives each 401 its true name — genuine
authentication failure vs anti-abuse trip — and makes the recovery structurally unable to
manufacture the duplicate placeholder rows plan 11-03 is cleaning up.

Output: an `AuraError` hierarchy with a real authentication type, a verify-then-retry branch
in `execute_plan`'s three write loops, retry cost and visibility counters, and an offline test
file that drives the whole path through `httpx.MockTransport`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI process → `api.pushd.com` | Every write response, including the retried one, is untrusted input that decides attribution |
| `AURA_EMAIL`/`AURA_PASSWORD` env → `/v5/login.json` | The re-login makes credential submission reachable mid-batch, on a code path that did not previously exist |
| `execute_plan` → `logs/file_{time}.log` | Every new exception message is a candidate log/stdout sink for secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-01 | Spoofing | `execute_plan` re-login path | medium | mitigate | At most ONE re-login per run, shared by all three write loops (run-scoped flag, Task 1/Task 3) — a hostile or MITM'd endpoint cannot farm one credential submission per chunk |
| T-11-02 | Information disclosure | `AuthenticationError` message | high | mitigate | The message interpolates only the failure class and `type(underlying).__name__`; never a response body, `auth_token`, or the password. Acceptance criterion asserts the message contains neither the password value nor `auth_token`; `_REDACT_KEYS` in `client.py` already masks both in logs |
| T-11-03 | Denial of service (self-inflicted) | retry branch | high | mitigate | One retry per chunk enforced by a per-chunk flag; one re-login per run enforced by a run-scoped flag; a second 401 hands off to `note_failure`, which still trips `ConsecutiveWriteFailureError` at 5. `retry_on_auth_401=False` is the kill switch |
| T-11-04 | Tampering | probe response deciding "already landed" | low | accept | A drifted or hostile probe response reporting a not-landed item as landed causes a missed upload, not a destructive act. md5 diffing is stateless, so the next `sync` run re-uploads it. Accepted rather than mitigated because the alternative (trusting absence) is the failure direction that created the 58 stuck rows |
