<objective>
Slice 1 of the live read-path verification: prove **login (READ-01)** and **frame listing (READ-02)** work against the live Aura API, and land the trust + security foundation that every live run depends on.

This plan makes the verification *trustworthy before it runs*: it adds `raise_for_status` so a real HTTP failure cannot masquerade as success (D-06), redacts the plaintext password / auth_token currently written to disk (D-07, the one HIGH-severity security item this phase), creates the missing `logs/` dir that otherwise crashes the first live run (D-08), registers the `live` pytest marker (D-01), and builds the session login fixture that auto-skips credential-less (D-02/D-03).

Purpose: Establish a credential-gated harness whose green/skip behavior is honest, then assert the first two read-path steps.
Output: Trust-edited `client.py`/`accountApi.py`/`aura.py`, `.gitignore` + `pyproject.toml` updates, new `tests/conftest.py` + `tests/test_read_path.py` (READ-01/02 tests).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shell env → process | `AURA_EMAIL`/`AURA_PASSWORD` enter via env vars; must never be persisted to VCS or logs |
| client → Aura API (`api.pushd.com`) | Untrusted, undocumented responses cross here; a drifted/failed response must not be processed as success |
| process → `logs/file_*.log` (disk at rest) | Structured request/response logging writes to disk; the login payload + response carry secrets |
