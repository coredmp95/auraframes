<objective>
Since the 0.5s per-write throttle landed in `execute_plan`, a large `sync --apply`
batch (e.g. 120 uploads) runs silently for many minutes between the dry-run plan
summary and the final result summary. The user reported the client "cannot stay
silent for 20 minutes" during a sync.

Add per-item progress feedback covering both the upload loop and the delete loop in
`execute_plan`, without breaking its offline-testable-by-injection design. Do this by
injecting a progress reporter/callback (default no-op) that `cli.py`'s `run_sync` wires
to a real tqdm-based bar, while offline tests inject a recording/no-op fake.

Purpose: give operators live feedback during long destructive applies.
Output: an injectable `progress` seam on `execute_plan`, a tqdm reporter in `run_sync`,
and offline test coverage of the seam.
</objective>

Key facts established by reading the sources:
- `execute_plan(plan, aura, frame_id, *, s3_client, sqs_client, throttle_seconds=..., sleep=time.sleep)`
  is the ONLY mutating function; it is offline-testable because `s3_client`, `sqs_client`
  and `sleep` are all injected. It re-raises `RateLimitError` to abort the whole batch and
  catches ordinary per-item exceptions into `result.upload_failures` / `result.delete_failures`.
- `cli.run_sync` constructs real `S3Client()`/`SQSClient()` only on confirmed `--apply`,
  then calls `execute_plan(...)` and prints a separated success/failure summary.
- `tqdm` is already a declared dependency (`pyproject.toml`); precedent usage is
  `for asset in tqdm(assets)` in `auraframes/aura.py`.
- `tests/test_cli_apply.py` monkeypatches `cli.execute_plan` with a fake whose signature is
  `fake_execute_plan(plan, aura, frame_id, *, s3_client, sqs_client)` — this signature MUST be
  updated when `run_sync` starts passing `progress=`.
- Tests run via `uv run pytest`.
</context>

<task type="auto" tdd="true">
  <name>Task 1: Add injectable progress reporter to execute_plan</name>
  <files>auraframes/sync.py, tests/test_execute_plan.py</files>
  <behavior>
    - Reporter is called once per attempted upload: progress('upload', path, True) on success,
      progress('upload', path, False) on a caught per-item failure.
    - Reporter is called once per attempted delete: progress('delete', asset.id, True) on success,
      progress('delete', asset.id, False) on a caught per-item failure.
    - Reporter is NOT called for an item that aborts the batch via RateLimitError (re-raise path).
    - Default reporter is a no-op; all existing execute_plan tests keep passing unchanged.
    - Upload reporter calls precede all delete reporter calls (mirrors D-09 ordering).
  </behavior>
  <action>
    Add a keyword-only parameter `progress` to `execute_plan`, defaulting to a no-op callable
    that accepts arbitrary args (a lambda ignoring its arguments). Place it alongside the
    existing injected `sleep` parameter so the offline-injection contract is extended, not
    changed. Document the new parameter in the docstring: it is called exactly once per
    attempted item with three positional arguments — a kind string ('upload' or 'delete'), the
    item identifier (the `Path` for uploads, the asset id string for deletes), and a boolean ok
    flag (True on success, False on a recorded per-item failure). State that it is deliberately
    NOT called on the RateLimitError abort path (the whole batch stops there) so the number of
    reporter calls equals attempted-and-resolved items only.

    In the upload loop: after `result.upload_succeeded += 1` call the reporter with the success
    triple; in the `except Exception` branch (after appending to `upload_failures`) call it with
    the failure triple. Leave the `except RateLimitError: raise` branch untouched — no reporter
    call there. Apply the symmetric change to the delete loop using the asset id as identifier.

    Keep the change minimal and local to the two loops — do not restructure the function, the
    throttle helper, or the RateLimitError handling. Per CLAUDE.md's pragmatic modernization
    constraint, this is a narrow seam addition, not a refactor.

    In tests/test_execute_plan.py add one test `test_execute_plan_reports_progress_per_item`
    that builds a plan with (e.g.) two uploads and one delete, injects a recording reporter that
    appends each (kind, identifier, ok) triple to a list, forces exactly one upload to fail
    (reuse the existing `_flaky_batch_update` monkeypatch pattern that fails the 'uploaded-1'
    item), and asserts: the recorded list has exactly len(to_upload)+len(to_delete) entries; the
    failed upload path is recorded with ok=False; the surviving upload and the delete are
    recorded with ok=True; and every 'upload' entry appears before every 'delete' entry.
  </action>
  <verify>
    <automated>uv run pytest tests/test_execute_plan.py -q</automated>
  </verify>
  <done>execute_plan accepts a no-op-defaulted `progress` reporter, calls it once per attempted
  upload/delete item with (kind, identifier, ok), never calls it on the RateLimitError abort path,
  and the new + existing test_execute_plan.py tests pass.</done>
</task>
