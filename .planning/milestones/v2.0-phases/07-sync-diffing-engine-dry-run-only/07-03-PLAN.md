<objective>
Perform the one-time LIVE validation required by SYNC-02 / success criterion 3:
confirm that hashing a photo's original bytes locally with `S3Client.get_md5`
produces exactly the `md5_hash` value the frame reports for the same photo. This
is the check that makes the whole diff engine trustworthy — if the two
base64-MD5 conventions differed by even one byte, every local file would look
"changed" forever, driving mass unwanted uploads/deletes (the "Hash-format
mismatch risk" logged in STATE.md).

Purpose: De-risk the engine before Phase 8 ever executes a plan. Following the
Phase 6 `md5_hash` live-spike methodology (D-09): piggyback on real usage, run
once, document the result in the project docs — do NOT add a permanent automated
regression fixture.

Output: A confirmed, documented finding in STATE.md and PROJECT.md.
</objective>

  <name>Task 1: Live-validate local get_md5 equals frame md5_hash (SYNC-02, D-09)</name>
  <what-built>
    Plans 01-02 delivered the dry-run sync engine (`auraframes/sync.py` +
    `aura-cli sync <dir> --frame <name|id>`), which hashes local files with
    `S3Client.get_md5` and compares them to frame asset `md5_hash` values. Before
    that comparison is trusted, SYNC-02 requires a one-time LIVE proof that the
    two hash conventions are byte-identical.
  </what-built>
  <how-to-verify>
    Run against a real Aura account/frame (requires live `AURA_EMAIL` /
    `AURA_PASSWORD` in the environment). Use whichever method fits what you have
    available — the goal is a single confirmed equality:

    METHOD A (preferred — piggyback on the feature itself, no throwaway script):
    1. Choose a photo for which you hold the exact ORIGINAL local file AND which
       is already present on a target frame (e.g. a photo you added to that frame
       from this same original file).
    2. Put that original file alone in a directory and run:
       `uv run aura-cli sync <that-dir> --frame <frame-name-or-id>`
    3. Confirm the plan reports that photo as UNCHANGED (unchanged count includes
       it, and it does NOT appear under uploads). Unchanged == the local
       get_md5 matched the frame's md5_hash exactly. If it shows as an upload,
       the conventions differ — STOP and report; the engine's assumption is
       broken.

    METHOD B (direct comparison, if you lack a known-matching original):
    1. Live-fetch one photo asset's `md5_hash` from a frame (e.g. via
       `uv run aura-cli --debug inspect --frame <x>` or `get_all_assets`).
    2. Obtain that same asset's ORIGINAL bytes (note: the image-proxy download
       path may re-encode — you must hash the original upload bytes, not a
       transformed rendition; record which source you used).
    3. Compute `get_md5(those_bytes)` and compare to the asset's `md5_hash`
       string. Confirm they are equal.

    Record: which method you used, the frame/asset involved (id only, no
    secrets), and the equal/not-equal result plus any caveat (e.g. image-proxy
    re-encoding observed).
  </how-to-verify>
  <resume-signal>
    Type "confirmed equal" (with the method used and asset id), or describe the
    mismatch/caveat you observed.
  </resume-signal>
