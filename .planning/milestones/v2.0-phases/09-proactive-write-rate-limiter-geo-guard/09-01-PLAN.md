<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → ipinfo.io | Untrusted third-party HTTP response (`_default_resolver`) drives a write-gating decision |
| process → local filesystem | Per-account budget state JSON is written to / read from disk |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Spoofing / Information Disclosure | `_default_resolver` (ipinfo.io/json) | low | mitigate | Short 4s timeout; `fail_open=True` default (deliberate availability>strictness tradeoff — an ipinfo outage/throttle must never block a legitimate upload); resolver is injectable so it can be replaced/disabled. A hijacked resolver returning a matching country only DISABLES the guard, it cannot enable a new write attack. |
| T-09-02 | Information Disclosure / Tampering | `WriteBudget.save`/`load` state file | low | mitigate | Persist ONLY `tokens` + `updated_at`; never the email (only its sha1-truncated hash, computed in 09-02, appears — in the filename, not the body), password, or auth tokens. Negative-assertion test confirms no credential material in the JSON body. Tampering with one's own local file only defeats one's own proactive protection (the reactive `RateLimitError`/`ConsecutiveWriteFailureError` backstop is unchanged), so it is not a security boundary. |
| T-09-SC | Tampering | pip/uv installs | low | accept | No new packages this phase (stdlib + existing `httpx` only, per RESEARCH.md Package Legitimacy Audit) — nothing to install, nothing to verify. |

(ASVS Level 1, block-on high. All threats here are low → none block execution.)
